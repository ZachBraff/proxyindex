Прокси для парсинга сайтов: какой тип выбрать под источник и объём

Автор — Сергей · опубликовано 16 ноября 2026

Прокси для парсинга выбирают по сайту-источнику и объёму: для обычных сайтов сравнение начинают с серверных IPv4, для большого потока запросов смотрят ротационные серверные, а резидентские берут, когда нужен город или версия страниц, которую видят посетители с домашним интернетом. Если у площадки есть официальный API, сначала проверьте его.

Какие прокси нужны для парсинга под вашу задачу

Тип прокси для сбора данных определяют три вещи: какой сайт вы собираете, сколько страниц в сутки и важна ли география ответа. Тариф и название пакета вторичны.

В таблице собраны типовые ситуации сбора открытых данных и тип, с которого разумно начать тест. Это стартовая точка: окончательный выбор подтверждает проверка на самом источнике.

Ситуация Что важно С чего начать сравнение
Каталоги и справочники без жёстких лимитов объём, стабильность серверные IPv4
Десятки тысяч страниц в сутки с одного сайта распределение потока ротационные серверные
Цены и наличие зависят от города адрес в нужном регионе резидентские с выбором города
Дата-центрам сайт показывает другую версию страниц данные как у обычного посетителя резидентские
Цепочки страниц с фильтрами и пагинацией один адрес на сессию sticky-сессии
Источник с официальным API условия API API площадки, прокси не нужны

Серверные IPv4 на 28 октября 2026 подтвердили 28 из 30 сервисов, их сравнение собрано в рейтинге серверных прокси IPv4. Для задач с географией и типом сети откройте рейтинг резидентских прокси: там только сервисы, у которых этот тип написан на их собственном сайте.

Сначала проверьте официальный API и robots.txt

Если у источника есть официальный API, прокси для этих данных обычно не нужны: вы получаете структурированный ответ по правилам площадки. Парсинг страниц начинают, когда API нет или в нём нет нужных полей.

Пример такого канала описан в документации Yandex Search API: сервис позволяет автоматически отправлять запросы к поисковой базе Яндекса и возвращает результаты в XML, HTML или JSON в зависимости от типа поиска. Если у вашего источника есть такой интерфейс, его условия читают до начала сбора.

Для страниц сайта правила для роботов задаёт файл robots.txt. Его формат описан в RFC 9309, и из стандарта для парсера следуют четыре вещи:

  • файл лежит по адресу /robots.txt в корне сайта;
  • если файл отдаёт ошибку 4xx, робот вправе обращаться к любым ресурсам сервера;
  • если сервер отвечает ошибкой 5xx, робот должен считать весь сайт закрытым;
  • кэшированную копию файла не стоит использовать дольше 24 часов.

RFC 9309 отдельно оговаривает, что эти правила не являются формой авторизации доступа. Поэтому кроме robots.txt прочитайте пользовательское соглашение площадки, а вопросы о допустимости сбора конкретных данных обсудите с юристом компании.

Серверные, ротационные или резидентские адреса

Серверные IPv4 принадлежат дата-центрам и хостинг-провайдерам, резидентские относятся к домашним подключениям у интернет-провайдеров. Ротационные серверные отличаются режимом: адрес из пула меняется по таймеру или на каждый запрос.

С серверных IPv4 удобно начинать, когда источник открыт и ровно отвечает на умеренный поток запросов. Адреса закреплены за вами на срок аренды, поэтому их легко добавить в список разрешённых и проще разбирать ошибки: каждый адрес виден в логах.

Ротационные серверные нужны, когда объём растёт и запросы удобнее раздавать по пулу, а не держать на нескольких закреплённых адресах. Ротация распределяет нагрузку, но не отменяет лимиты сайта: темп запросов к одному источнику всё равно задаёте вы.

Резидентские адреса рассматривают в двух случаях. Первый: содержимое страницы зависит от региона посетителя, и нужен адрес в конкретном городе. Второй: на тесте видно, что адресам дата-центров сайт показывает другую версию страниц, а вам нужны данные в том виде, в каком их видят покупатели.

Ротация или sticky-сессии

Ротация подходит для независимых запросов, sticky-сессия (один IP на время сессии) нужна, когда несколько запросов подряд должны идти с одного адреса. Ошибка в выборе режима видна сразу: сессия рвётся, выбранный город или фильтры сбрасываются.

Независимые запросы — это карточки товаров, страницы справочника, отдельные URL из карты сайта. Каждый запрос самодостаточен, поэтому смена адреса между ними ничего не ломает.

Цепочки запросов ведут себя иначе. Пагинация с фильтрами и выбор города на сайте требуют, чтобы cookie и адрес не менялись до конца цепочки.

Это видно и по инструментам. В документации requests сказано, что объект Session сохраняет cookie между запросами и переиспользует TCP-соединение с тем же хостом. Прокси можно передать в отдельный запрос аргументом proxies или один раз задать для всей сессии.

Если страницы собираются через браузер, прокси в Playwright задают для всего браузера или для отдельного контекста, с логином и паролем для HTTP(S)-прокси. Отдельный контекст с отдельным прокси удобен, когда несколько потоков сбора работают параллельно и не должны смешивать cookie.

Оплата за IP или за трафик

Модель оплаты зависит от того, сколько байт уходит на одну страницу. За IP платят за число адресов на срок, при оплате по факту трафика (pay-as-you-go) списывается израсходованный объём, и тогда вес страницы прямо влияет на счёт.

Вес страницы сильно зависит от способа сбора. По данным HTTP Archive Web Almanac 2024, медианная внутренняя страница на десктопе загружает 18 КБ HTML. Медианный вес десктопной страницы целиком, со стилями, скриптами и картинками, в замере октября 2024 составил 2 652 КБ.

HTTP-клиент вроде requests скачивает только HTML, если вы не запрашиваете остальные файлы. Браузер загружает страницу целиком. Разница по медианам: 2 652 КБ против 18 КБ, больше чем в 147 раз.

Условный пример расчёта трафика

Условный пример: компании нужно раз в сутки собирать 10 000 страниц каталога с одного сайта. Цифры веса взяты из медиан Web Almanac, у вашего источника они будут другими.

  • Только HTML: 10 000 × 18 КБ = 180 000 КБ, это 180 МБ в сутки и 5,4 ГБ за 30 дней.
  • Браузер со всеми файлами: 10 000 × 2 652 КБ = 26 520 000 КБ, это 26,52 ГБ в сутки и 795,6 ГБ за 30 дней.
  • Оценка для браузера верхняя: часть файлов он берёт из кэша, а картинки можно не загружать.

Отсюда практическое правило. Если данные есть в HTML, оплата по трафику обычно не страшна. Если без браузера не обойтись, сначала измерьте трафик на одну страницу на тесте и только потом сравнивайте тарифы за гигабайт с тарифами за IP.

Когда проще scraping API

Scraping API (API для сбора данных) нужен, когда вы не хотите сами держать парсер, браузеры и пул адресов: вы отправляете URL и получаете готовый ответ. Это другой продукт, чем прокси, и сравнивать его надо по стоимости одной успешной страницы.

В рейтинге scraping API — отдельное условие среди типов прокси. Сервисы, которые подтвердили его на своём сайте, перечислены в разделе с данными рейтинга ниже.

Scraping API разумно рассмотреть в трёх случаях:

  • источников много, и поддерживать отдельный парсер под каждый дорого;
  • страницы собираются только с выполнением JavaScript;
  • в команде нет разработчика, который будет следить за сбором.

Если источник один, данные лежат в HTML и разработчик есть, своих прокси и HTTP-клиента обычно хватает. Тогда в работе остаются API управления прокси (выдача и смена адресов из кода) и подаккаунты для сотрудников.

Как держать темп запросов к источнику

Темп задаёт парсер, а не прокси: даже с большим пулом адресов источник вправе ограничить частоту запросов. Сигналы сайта нужно читать и замедляться, а не менять адрес.

Главный такой сигнал описан в справке MDN о коде 429: ответ значит, что клиент отправил слишком много запросов за отрезок времени. Механизм просьбы снизить частоту называют rate limiting.

К ответу 429 сервер может добавить заголовок Retry-After. В нём указано, сколько ждать до следующего запроса: числом секунд или датой. Парсер должен прочитать заголовок и выдержать паузу.

Две настройки requests стоит задать явно, потому что по умолчанию их нет. Документация requests предупреждает, что запросы без таймаута не прерываются и код может зависнуть на минуты. Повторов при сбое соединения библиотека тоже не делает, их подключают через класс Retry из urllib3 с паузами между попытками.

Как проверить выбранный тип на своём источнике

Тест на реальном источнике отвечает на вопрос, который не закрывает ни сайт сервиса, ни рейтинг: подходит ли тип адресов именно вашему сайту. Проводите его с тем же темпом, городами и способом сбора, что и в работе.

За тест запишите четыре числа:

  • долю ответов 200 от всех запросов;
  • сколько раз пришёл ответ 429 и что было в Retry-After;
  • среднее время ответа;
  • трафик на одну страницу, если тариф считается за гигабайты.

Если серверные адреса дают стабильные ответы, переходить на другой тип незачем. Если нет, повторите тест на резидентских с тем же объёмом и сравните те же четыре числа. Как устроить пробную закупку и что проверить в условиях сервиса до оплаты, разобрано в статье о выборе прокси для компании.

Вопросы и ответы

Какие прокси нужны для парсинга?
Для открытых каталогов и справочников с умеренным потоком запросов сравнение начинают с серверных IPv4. При большом объёме с одного сайта смотрят ротационные серверные, а резидентские берут, если ответ зависит от города или сайт показывает адресам дата-центров другую версию страниц. Окончательный выбор подтверждает тест на самом источнике.
Нужны ли ротационные прокси для парсинга сайтов?
Они нужны, когда запросов много и их удобнее раздавать по пулу адресов, а каждый запрос независим, как карточки товаров или страницы справочника. Для цепочек с cookie, фильтрами и выбором города нужна sticky-сессия. Ротация не отменяет лимиты сайта: темп запросов всё равно задаёт ваш парсер.
Что выгоднее для сбора данных: оплата за IP или за трафик?
Это зависит от веса страницы при вашем способе сбора. Если данные есть в HTML, трафика уходит немного, и оплата за гигабайты обычно подходит. Если страницы открываются в браузере со всеми файлами, по медианам Web Almanac 2024 объём растёт больше чем в 147 раз, поэтому сначала измерьте трафик на одну страницу на тесте, а потом сравнивайте тарифы.
Чем scraping API отличается от прокси для парсера?
Прокси дают только адреса, а парсер, браузер и обработку ответов вы держите сами. Scraping API берёт загрузку страниц на себя: вы передаёте URL и получаете готовый ответ. По данным ПроксиИндекса на 28 октября 2026, такой продукт на своём сайте подтвердили 5 сервисов из 30.
Что делать, если сайт отвечает кодом 429?
Код 429 означает, что клиент отправил слишком много запросов за отрезок времени. Прочитайте заголовок Retry-After, если сервер его прислал: там указана пауза в секундах или дата. Снизьте темп запросов к этому источнику и задайте в коде таймауты и повторы с паузами.
